# 02: Licensing facts for ModelingToolkit v11 (research)

Ticket: `.scratch/mtk-upgrade/issues/02-licensing-facts.md`. Researched 2026-10-14 against MTK **v11.45.4**, ModelingToolkitBase (MTKBase) **v1.77.4**, StateSelection **v1.11.1**, ModelingToolkitTearing **v1.20.7**. Not legal advice: the sections below only report what the licenses and the maintainers say.

## Summary

1. Full MTK v11.45.4 pulls in exactly **two AGPL-3.0 packages**: **StateSelection.jl** and **ModelingToolkitTearing.jl** (repo `JuliaComputing/StateSelection.jl`). Both are **hard `[deps]`** of MTK, not weak deps or extensions, and MTK imports them at load time. They were AGPL from their first registered releases (StateSelection v1.0.0, 2025-12-02; MTKTearing v1.0.0, 2025-12-09). MTK has depended on them since **v11.0.0** (2025-12-11). MTK ≤ v10.32.1 does not depend on them.
2. No other package in the closure is AGPL or GPL. The closure of both full MTK and MTKBase alone also contains **weak-copyleft** packages: MPL-2.0 (Krylov, AMD, MutableArithmetics) and LGPL-2.1+ (PureKLU, via LinearSolve). Julia's bundled SuiteSparse binaries (used by SparseArrays, which MTKBase and BondGraph already use) include GPL-2.0+ modules.
3. MTK's own code, and MTKBase, stay MIT. SciML's position (NEWS, blog post, Discourse) is that you keep whatever license you choose for your own code. Rackauckas (personal view, citing a NumFOCUS lawyer consultation): an AGPL dependency means the package "is effectively shipping as AGPL" for people who build or redistribute it. Isaacson (personal view, which he says the council does not share as a consensus): your library "needs to be AGPL". **The SciML steering council explicitly gives no legal guidance** and tells people to consult a lawyer.
4. MTKBase has: `System`, codegen, problems, initialization, and a "very barebones" `mtkcompile` that requires `D(x) ~ rhs` explicit form and moves explicit `lhs ~ f(states, observed)` equations into observed. MTKBase has **no** Pantelides/dummy-derivative index reduction, Bareiss alias elimination, matching-based tearing, or structural-singularity removal. Loading `ModelingToolkit` swaps in the full pipeline by pirating `MTKBase.__mtkcompile`.
5. Measured in experiments, MTKBase alone: index-1 junction models simulate correctly but keep implicit junction equations as mass-matrix DAE rows. A coupled-inertia (index-2) model happens to integrate with consistent ICs, but gives a `SingularException` or wrong algebraic initial values with inconsistent ICs. An I-element written in derivative causality compiles silently, then fails at `ODEProblem` with `Symbol f2ˍt(t) is not present`. Full MTK reduces all of these to index-0 ODEs.
6. JOSS requires the *submitted software* to carry an OSI-approved license. Apache-2.0, MIT, AGPL-3.0, MPL-2.0 and LGPL-2.1 are all OSI-approved. JOSS documents no rule on dependency licenses.
7. Precedent: **Catalyst.jl** switched its dependency to MTKBase only "to remain fully MIT-licensed", and tells users to `using ModelingToolkit` themselves if they want the full reduction.

## 1. Which packages in MTK v11 are copyleft

### Method

Resolved `ModelingToolkit@11.45.4` in a fresh environment on Julia 1.12.6 with the General registry as of 2026-10-14 (180 packages including stdlibs). Read the `LICENSE*`/`COPYING` file of every installed package. Repeated this for `ModelingToolkitBase@1.77.4` alone (185 entries). For each copyleft hit, looked up which packages require it with `Pkg.dependencies()`. JLL binary artifacts and stdlibs carry no package-level LICENSE file. For those, Julia's `THIRDPARTY.md` is used instead (see below).

So `Pkg.add("ModelingToolkit")` always installs them and `using ModelingToolkit` always loads them.

It is absent from the resolved manifest and from Project.toml.

The MTK README at v11.45.4 says nothing about licensing or AGPL. [Issue #4217](https://github.com/SciML/ModelingToolkit.jl/issues/4217), which asked for a note, was closed 2026-05-25 without one.

## 2. What it implies for a package depending on full MTK, and what SciML says

### Official / maintainer statements (quoted or paraphrased, with source)

- **MTK NEWS.md, "Splitting into `ModelingToolkitBase` and relicensing of parts of ModelingToolkit"** ([v11.45.4 NEWS.md L337-353](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/NEWS.md#L337)): index reduction, structural singularity removal and tearing "are now moved to … StateSelection.jl and ModelingToolkitTearing.jl … These packages are AGPL licensed." MTKBase keeps `System`, callbacks, codegen/problem constructors and initialization. Items that need structural simplification (e.g. `SCCNonlinearProblem`) moved to ModelingToolkit, "which depends on the aforementioned AGPL packages".
- **SciML blog, "ModelingToolkit v11: Licensing, …"** (Rackauckas, published 2026-07-27; [source](https://github.com/SciML/sciml.ai/blob/master/news/2026/07/27/ModelingToolkitv11.md), merged via [sciml.ai#243](https://github.com/SciML/sciml.ai/pull/243)):
  - "ModelingToolkitBase.jl is a new, MIT-licensed package with no Julia AGPL dependencies" (L41).
  - Index reduction, structural singularity removal, "and the advanced tearing and alias elimination passes" went to the AGPL packages. "A basic tearing pass is still included in MTKBase … so simple acausal models, handling of observed equations, etc. will all still work under the fully MIT version" (L47-50).
  - "If you are redistributing ModelingToolkit.jl in a shipped binary or web service, then you need to ensure the licensing requirements of AGPL are satisfied … If one only installs and uses ModelingToolkitBase.jl, then the underlying library is still MIT, and has the same permissiveness as ModelingToolkit v10" (L54-57).
  - "ModelingToolkitBase.jl is a GPL-free core version that libraries such as Catalyst.jl and SymBoltz.jl can directly depend on, while the acausal modeling capabilities still work without any changes to user code by just doing `using ModelingToolkit`" (L110-112).
- **Steering council announcement** (Isaacson, [Discourse 134396 #1](https://discourse.julialang.org/t/modelingtoolkit-v11-library-split-and-licensing-community-feedback-requested/134396), 2025-12-06): "Libraries, notebooks, and scripts that only use the new MIT MTKBase library will have no new restrictions." For the AGPL add-on, "the exact implications … will depend on how one is using them. Note that many companies, and some institutions, have policies against AGPL software … As non-lawyers, we encourage consulting with legal counsel."
- **No legal FAQ exists.** The council asked a lawyer via NumFOCUS but "can not provide any substantive guidance about this (and will not be able to)" ([#19](https://discourse.julialang.org/t/134396/19), [#60](https://discourse.julialang.org/t/134396/60)). A "public faq" was promised in [#10](https://discourse.julialang.org/t/134396/10). A code search of the SciML org and sciml.ai finds AGPL mentioned only in NEWS, the blog, and Catalyst, so the FAQ was not found (**UNVERIFIED** that it does not exist elsewhere). Rackauckas listed open items such as "Licensing of exported code and FMUs" in [#66](https://discourse.julialang.org/t/134396/66). Nothing was found showing these were resolved.
- **The two maintainers disagree on what a downstream library inherits**, and both call their view personal:
  - Rackauckas ([#48](https://discourse.julialang.org/t/134396/48)): "if you `using SOME_AGPL_LIBRARY` … as a dependency in my public Julia library, then your library is effectively shipping as AGPL. That does not mean you cannot make the copyright of your own code MIT … But having an AGPL dependency means that someone building with this code needs to follow the AGPL practices." In [#46](https://discourse.julialang.org/t/134396/46) he adds: "You can always copyright your own code to whatever license you want." "An extension that isn't triggered does not imply GPL." For test-only dependencies, "If you are not shipping any AGPL dependencies, then AGPL licensing does not apply." He calls this his own interpretation of a Q&A that was "checked and confirmed with a lawyer provided by NumFOCUS". In [#37](https://discourse.julialang.org/t/134396/37): "if you open source your code to a GPL-compatible license (such as MIT) then a change of a dependency to GPL has no impact."
  - Isaacson ([#47](https://discourse.julialang.org/t/134396/47)): "if I `using SOME_AGPL_LIBRARY` … in my public Julia library, my library needs to be AGPL." He labels this "my personal interpretation, and not any consensus from the SciML steering council". In [#40](https://discourse.julialang.org/t/134396/40) he says Rackauckas's comments "do not reflect any consensus among the SciML steering council".
  - Why AGPL and not LGPL: "AGPL is the most permissive license that would be accepted … We proposed LGPL but that was not found to adequately address those issues" ([#45](https://discourse.julialang.org/t/134396/45)).
- **Status check** ([#134](https://discourse.julialang.org/t/134396/134), Oscar Smith, 2026-05-22): "MTK still is MIT licensed, but it depends on … StateSelection.jl … which is AGPL."

### Facts relevant to BondGraph's own license (Apache-2.0)

- License compatibility, per FSF: Apache-2.0 is "compatible with version 3 of the GNU GPL" and not with GPLv2. AGPLv3 is "not compatible with GPLv2", but "you are allowed to combine separate modules or source files released under both [AGPLv3 and GPLv3]" ([FSF license list, #apache2 and #AGPLv3.0](https://www.gnu.org/licenses/license-list.html)). Stefan Karpinski says the same about GPLv2 in [#51](https://discourse.julialang.org/t/134396/51).
- Julia packages never vendor their dependencies. BondGraph's repository would contain only BondGraph's code, and Pkg downloads StateSelection/MTKTearing separately from their own repositories. Whether that removes any obligation is exactly the point the two maintainers disagree on above. **No legal conclusion is drawn here.**
- An architectural fact that matters for the stance decision (ticket 07): MTK customizes compilation by **type piracy of `MTKBase.__mtkcompile`**. "ModelingToolkit.jl then pirates `__mtkcompile` to define the advanced simplification. It is the only package allowed to do so" ([docs/src/internals/mtkcompile.md L26](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/docs/src/internals/mtkcompile.md); code: [src/systems/systems.jl L1](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/src/systems/systems.jl#L1)). So a package that depends only on MTKBase and calls `mtkcompile` gets **full** index reduction whenever the *user* also runs `using ModelingToolkit` in the same session. This is the Catalyst pattern.

## 3. MTKBase vs full MTK: concrete capabilities

### What MTKBase's `__mtkcompile` does ([lib/ModelingToolkitBase/src/systems/systems.jl](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/lib/ModelingToolkitBase/src/systems/systems.jl), L227-504)

1. `expand_connections`, discrete→parameter conversion, limited-operator lowering. Connection expansion is in MTKBase, so `connect` works.
2. **Balance check by counting only**: it throws `ExtraEquationsSystemException`, or `ExtraVariablesSystemException` with the text "This may also be a high-index DAE, which ModelingToolkitBase.jl cannot handle. Consider using ModelingToolkit.jl" (L283-305). It does no structural (matching) analysis.
3. Equations are classified by **syntax**: `isdiffeq(eq) = isdifferential(eq.lhs) || …` ([utils.jl L739](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/lib/ModelingToolkitBase/src/utils.jl#L739)). Higher-order `D^n(x)` equations get simple order reduction (L358).
4. **"Trivial tearing"** (`get_trivial_observed_equations!`, L517-590): an algebraic equation becomes observed only if its **LHS is an unknown** and its RHS depends only on differential variables or already-observed variables. This repeats until nothing changes. It never solves an equation for a variable that is not on the LHS.
5. Everything left over stays as `0 ~ rhs - lhs` algebraic rows, so the result is a mass-matrix DAE. Any `Differential` left on an RHS throws "ModelingToolkitBase.jl is unable to simplify such systems. Encountered derivative in RHS of equation … Please consider using ModelingToolkit.jl" (L470-486). The docs describe this as "very barebones … supports explicit differential equations of the form `D(x) ~ ...` and performs a very basic version of tearing" ([mtkcompile.md L12-22](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/docs/src/internals/mtkcompile.md)), and NEWS says it "does not perform index reduction and requires that all differential equations are explicit in the derivative" (L345-347).

| Capability | MTKBase (MIT) | Full MTK (adds AGPL StateSelection / MTKTearing) |
|---|---|---|
| `System`, `connect` expansion, codegen, `ODEProblem` etc. | Yes | Yes |
| Initialization system (`initial_conditions`, `guesses`, `bindings`) | Yes, compiled with the same basic `mtkcompile` ([initializationproblem.jl L205](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/lib/ModelingToolkitBase/src/problems/initializationproblem.jl#L205)). Underdetermined init falls back to least squares | Yes, with the full pipeline |
| Alias elimination | Only what the LHS-explicit trivial tearing catches | `eliminate_perfect_aliases!`, Bareiss-based `alias_elimination!` ([mtkcompile.md L65-99](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/docs/src/internals/mtkcompile.md)) |
| Tearing | LHS-explicit substitution only | Matching-based, `CarpanzanoTearing`, SCC-wise (L164-198) |
| Index reduction | **None** | Pantelides + dummy derivatives via `StateSelection.dummy_derivative_graph!` (L124-162). `StructuralTransformations` exports `dae_index_lowering`, `dummy_derivative`, `pantelides_reassemble` ([src/structural_transformation](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/src/structural_transformation/StructuralTransformations.jl)) |
| Structural singularity removal | None | Yes (NEWS L339) |
| `SCCNonlinearProblem` | No (moved to MTK) | Yes |

### Experiment: plain-equation bond graphs on MTKBase vs MTK

Setup: Julia 1.12.6, MTKBase 1.77.4 alone, then MTK 11.45.4 + MTKBase 1.77.4, with `OrdinaryDiffEqRosenbrock` (`Rodas5P`) and `OrdinaryDiffEqNonlinearSolve`. The equations mimic what a BondGraph junction expansion produces, written with `@variables`, `System(eqs, t)`, `mtkcompile` and `ODEProblem(cs, u0, (0.0, 1.0))`. MTKBase requires `OrdinaryDiffEqNonlinearSolve` to be loaded as soon as an algebraic row remains. Without it you get "This ODE requires a DAE initialization and thus a nonlinear solve but no nonlinear solve has been loaded."

| Model | MTKBase result | Full MTK result |
|---|---|---|
| (1) Se→1-junction→I,C,R. The junction effort sum is written `e_se ~ e_i + e_c + e_r`, which is index 1 | States `[p, q, e_i]` plus one algebraic row `0 ~ e_c + e_i + e_r - e_se`. Solves, `Success`, and agrees with MTK to 1e-9 | Index-0 ODE in `[f_c, q]`, `Success` |
| (1b) Same, but the effort sum written solved for `e_i` (`e_i ~ e_se - e_c - e_r`) | Pure ODE in `[p, q]`, `Success`. **Whether MTKBase gets an ODE or a DAE depends on which side of `~` the junction equation puts the variable** | Same ODE |
| (2) Se→1-junction→I1,I2. Two inertias rigidly coupled, so the second I is in derivative causality. The constraint `0 ~ f1 - f2` contains only differential variables, so this is **index 2** | Compiles **without any warning** to states `[p1, p2, e1, e2]` with rows `0 ~ f1 - f2`, `0 ~ e1 + e2 - e_se`. With consistent ICs (`p1=p2=0`), `Rodas5P` returns `Success` with the correct answer `p=(0.25, 0.75)`. With inconsistent ICs (`p1=1, p2=0`) it throws `LinearAlgebra.SingularException(4)`. With only `p1=1` given, the init is "underdetermined … default to using least squares" and gives the wrong algebraic init `e1=e2=0.5` (correct: 0.25/0.75), although the states recover | Index-reduced: states `[p2, p1ˍt]` (dummy derivative). `Success`, `p2(1)=0.75` |
| (3) I2 written directly in derivative causality, `e2 ~ m2*D(f2)` | `mtkcompile` **succeeds silently**. `ODEProblem` then throws `ArgumentError: Symbol f2ˍt(t) is not present in the system.` | 1-state ODE `D(p1) ~ e_se/4`, `Success`, `p1(1)=0.25` (exact) |

What follows for bond graphs (bullets 1, 2 and 4 are inferences from the code and runs above; bullet 3 is measured):

- Junction structures produce many `x ~ y` and sum equations. MTKBase eliminates only those whose LHS is a not-yet-determined unknown. The rest become algebraic rows, which gives larger mass-matrix DAEs. These still need a stiff or DAE solver plus a nonlinear solver for initialization, while full MTK gives an explicit ODE.
- Models that are **index 1** after junction expansion work on MTKBase. That covers all-integral causality, and algebraic loops through R elements.
- Models with **storage elements in derivative causality** (dependent I or C states) are index ≥ 2. MTKBase does not detect them (the counting check passes) and does not reduce them. Depending on how the element equations are written, they fail at problem construction (case 3), fail at initialization (case 2, inconsistent ICs), or run with unreliable algebraic initialization. Success in case 2 is specific to a linear, consistent example and should not be generalized (**UNVERIFIED** for nonlinear cases).
- BondGraph's current `adjmtx2eqs` output form (which side of `~` each variable is on) would decide how much MTKBase can tear. **UNVERIFIED** for the actual BondGraph examples, which have not been run on MTKBase.

## 4. Software paper (JOSS)

- JOSS submission requirement: "The software must be open source as per the [OSI definition](https://opensource.org/osd)" ([docs/submitting.md L8](https://github.com/openjournals/joss/blob/main/docs/submitting.md), commit 3bdbe7d086, 2026-07-13). Review criterion: "There should be an OSI approved license included in the repository … an actual license file present" ([docs/review_criteria.md L24-29](https://github.com/openjournals/joss/blob/main/docs/review_criteria.md)). JOSS also says: "Software should use an OSI-approved license" ([docs/paper.md L307](https://github.com/openjournals/joss/blob/main/docs/paper.md)).
- These requirements apply to **the submitted repository's license**. Neither file mentions dependency licenses. On dependencies they ask only that they be "clearly documented and their installation handled by an automated procedure" (review_criteria L125). JOSS's stance on proprietary toolchains is that they are "strongly prefer[red]" against but acceptable if the submission has "a valid open source license" (submitting.md L140-142). By that reading, a fully open AGPL dependency is less of an issue than a proprietary one (this is an inference, not stated by JOSS).
- AGPL-3.0, Apache-2.0, MPL-2.0 and LGPL-2.1 all have OSI license pages ([agpl-v3](https://opensource.org/license/agpl-v3), [apache-2-0](https://opensource.org/license/apache-2-0), [mpl-2-0](https://opensource.org/license/mpl-2-0), [lgpl-2-1](https://opensource.org/license/lgpl-2-1)). The SciML blog also says "AGPL is an OSI-approved license" (L52).
- **UNVERIFIED / not found:** any JOSS policy or editorial decision on submissions with AGPL dependencies. Other venues (e.g. a thesis-related journal) were not checked.

## Gaps / UNVERIFIED

- No official SciML legal FAQ was found. The maintainers' opinions on inheritance conflict (§2).
- How MTK-generated code and FMUs are licensed under the AGPL passes is an open question raised by the maintainers ([#46](https://discourse.julialang.org/t/134396/46), [#66](https://discourse.julialang.org/t/134396/66)).
- Licenses of binaries inside non-stdlib JLL artifacts in the closure were not audited.
- The behaviour of the real BondGraph examples on MTKBase is untested. The experiments above use hand-written equivalent equations.
