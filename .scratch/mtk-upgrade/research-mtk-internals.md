# Research: MTK / Symbolics / SymbolicUtils internals used by BondGraph.jl, 8.71 → current

Date: 2026-10-14. Scope: `src/BondGraph.jl`, `src/mtk.jl`, `src/types.jl`, `src/bg.jl`, `src/utils/*.jl` (not `src/mbg.jl`).
Method: old sources read from the 8.71.2 tarball on disk (identical to tag `v8.71.2`); current sources read from shallow clones of tags `ModelingToolkit.jl v11.45.4`, `Symbolics.jl v7.45.0`, `SymbolicUtils.jl v4.51.0`, plus `gh api` for intermediate tags and release notes. Nothing was executed in Julia. Claims that would need a run to confirm are marked **UNVERIFIED**.

## Executive summary

1. Latest releases as of 2026-10-14: **ModelingToolkit v11.45.4** (with **ModelingToolkitBase v1.77.4** in `lib/`), **Symbolics v7.45.0**, **SymbolicUtils v4.51.0**. All three require **Julia ≥ 1.10**.
2. `src/mtk.jl` overwrites 4 MTK methods: `expand_connections`, `generate_connection_set`, `split_assign`, `single_named_expr`. Julia 1.10+ rejects that during precompilation ([julia v1.10.0 gf.c#L1572](https://github.com/JuliaLang/julia/blob/v1.10.0/src/gf.c#L1572)).
3. The connection layer BondGraph hooks into was **rewritten in MTK v10.4.0** ([PR #3736](https://github.com/SciML/ModelingToolkit.jl/pull/3736)). `ConnectionSet`, `ConnectionElement`, `namespaced_var` and the `find`/`replace` arguments no longer exist. Connection sets are now connected components of a hypergraph of `ConnectionVertex`, so the order of arguments inside `connect` (BondGraph's bond direction) is lost.
4. MTK has **no public extension point for custom connection semantics**. Only `Equality`, `Flow`, `Stream` (and causal input/output) are documented. A custom type such as `connect = bg` silently falls into the `Equality` branch and produces `e₁ ~ e₂, f₁ ~ f₂`, which is wrong for bond graphs.
5. `mtkcompile` and `complete` call MTK's own `expand_connections` internally. So BondGraph must **remove its bond `connect` equations before MTK sees the system**. It can do that with a non-overwriting pre-pass built on documented API (`Connection`, `get_eqs`, `get_systems`, `@set!`, `renamespace`). This is the recommended replacement for `src/mtk.jl`.
6. Since v10.0.0, `mtkcompile` throws if an equation contains a variable that is not an unknown of the system. BondGraph's generated bond variables (`a▶b₊f`, made with `rename`) must therefore be declared as unknowns. On 8.71 they were discovered automatically.
7. SymbolicUtils changes: `istree` became `iscall` (SU 2.0); `similarterm` became `maketerm` (deprecated in SU 2.0, gone in SU 3.0); the abstract type `Symbolic` was removed in SU 4.0. In Symbolics 7, `unwrap` now returns `BasicSymbolic` even for constants (wrapped as `Const`).
8. Other MTK changes: `states`→`unknowns` (v9); `ODESystem`→`System` and `structural_simplify`→`mtkcompile` (v10, both still accepted as deprecated aliases in v11.45.4); `defaults`/`get_defaults` removed in favour of `initial_conditions`/`bindings` (v11); `@parameters F(t)` is now an error and must be `@discretes F(t)` (v11); `@variables t` as the independent variable now warns.
9. The broken fresh resolve (new TimerOutputs vs old Groebner) goes away on the new stack: Groebner is only a weak dependency of Symbolics 7.
10. **Recommendation:** target MTK v11 / Symbolics 7 / SymbolicUtils 4 / Julia 1.10. Replace `src/mtk.jl` with a BondGraph-owned `expand_bonds` pre-pass and drop the tuple form of `@named`. The riskiest step is re-implementing bond extraction and sign/direction handling on the new API while keeping the 221 tests' equations identical.

The other imports in `mtk.jl` (`namespace_equation(s)`, `namespace_expr`, `independent_variables`, `isvariable`, `renamespace`, `istree`, `arguments`, `symtype`, `operation`, `similarterm`, `getmetadata`, `setmetadata`, `getname`, `Symbolic`, `FnType`, `equations`) are used only by the **commented-out** code (`src/mtk.jl:99-244`) or elsewhere through the module namespace.

Why this fails on Julia ≥ 1.10: overwriting a method during precompilation used to print a warning ("incremental compilation may be fatally broken", [julia v1.9.0 gf.c#L1478](https://github.com/JuliaLang/julia/blob/v1.9.0/src/gf.c#L1478)). Since 1.10 it is an error: "Method overwriting is not permitted during Module precompilation" ([julia v1.10.0 gf.c#L1572](https://github.com/JuliaLang/julia/blob/v1.10.0/src/gf.c#L1572); see also [JuliaLang/julia#52214](https://github.com/JuliaLang/julia/pull/52214)).

Context (not investigated further): a fresh resolve of the old stack fails because new TimerOutputs breaks the old Groebner pulled in by Symbolics 5 (`.scratch/roadmap.md`). Symbolics 5.8.0 had Groebner as a hard dependency ([v5.8.0 Project.toml](https://github.com/JuliaSymbolics/Symbolics.jl/blob/v5.8.0/Project.toml)). In Symbolics 7.0.0 both Groebner and Latexify are weak dependencies (package extensions) ([v7.0.0 Project.toml](https://github.com/JuliaSymbolics/Symbolics.jl/blob/v7.0.0/Project.toml)), so the problem does not apply to the target stack.

## 3. MTK's connection system today and how to replace `src/mtk.jl`

**Structure (v11.45.4).** `expand_connections` (MTKB `systems/connectors.jl#L1059-L1122`) runs these steps:
1. `remove_analysis_points`.
2. `generate_connection_set(sys)` (L687). This recursively walks the hierarchy (`_generate_connection_set!`, L784). For every `connect` equation, `handle_maybe_connect_equation!` (L710-L760) adds one hyperedge per connector variable to `ConnectionState.connection_graph` and one system hyperedge to the domain graph.
3. Connection sets = `Graphs.connected_components` of the hypergraph (connectiongraph.jl#L392), i.e. **merged and unordered**.
4. `generate_connection_equations_and_stream_connections(sys, csets)` (L883): Flow → `0 ~ Σ±v`; causal → `v ~ root`; Stream → instream; **anything else → Equality** (L941).
5. `expand_instream`, then `get_domain_bindings`, then `flatten`.

`mtkcompile` ([src/systems/systems.jl#L10](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/src/systems/systems.jl#L10)) and `complete` (MTKB `systems/abstractsystem.jl#L662`) both call `expand_connections` themselves.

**Is there a supported extension point?** No.
- The docs list only `Equality`, `Flow`, `Stream` (+ `instream`) as connection semantics ([model_building.md#L82-L116](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/docs/src/API/model_building.md)).
- `ConnectionVertex.type` is documented as "One of `Stream`, `Equality`, `Flow`, `InputVar`, `OutputVar`" (connectiongraph.jl#L24-L31).
- `AbstractConnectionState` is abstract, but `generate_connection_set!` is typed on the concrete `ConnectionState`/`NegativeConnectionState` (L770).
- The `AbstractSystem` docs say custom system types "should not extend internal compilation or problem-construction functions" (MTKB `ModelingToolkitBase.jl#L195-L209`).
- Analysis points (`AnalysisPoint`, `ignored_connections`) only *remove* causal connections; they cannot express junction semantics.

Approaches (no method overwriting in any of them):

| # | Approach | Pros | Cons |
|---|---|---|---|
| **A (recommended)** | **BondGraph pre-pass `expand_bonds(sys)`**. Walk the hierarchy via `get_systems`/`get_eqs`. For each `eq` with `Symbolics.value(eq.lhs) isa Connection` whose connectors carry BG metadata, take the **ordered** `get_systems(rhs)` (order kept by `connect`, MTKB connectors.jl#L25-L39). Build namespaced `e`/`f` with `renamespace`, collect a `Vector{Bond}`, and remove those equations with `@set! sys.eqs`. Then reuse the existing `csets2adjmtx`/`adjmtx2eqs` logic (adapted from `ConnectionElement` to `Bond`) to produce equations. Add the generated bond variables to unknowns and the equations to the root, then call `mtkcompile`. `simplifysys` = `mtkcompile(expand_bonds(sys))`; `generate_graph` uses the same bond list. | Uses only exported or documented API (`Connection`, `connect`, `get_eqs`, `get_systems`, `renamespace`, `@set!`, `System`). Keeps today's user API (`Junction0/1`, `connect` between `.power` ports) and the BG algorithm. Precompiles. Independent of MTK's hypergraph internals, which have already been rewritten once. | The user **must** call `expand_bonds`/`simplifysys` before `mtkcompile`/`complete`. Calling `mtkcompile(mdl)` directly silently produces `Equality` equations (wrong physics). Mitigation: give `Power` variables a BG-specific check and add a `bgcompile` wrapper; documentation. Requires rewriting `graph.jl`/`connection_utils.jl` and `test_graph.jl`, which use `ConnectionSet`/`ConnectionElement`/`namespaced_var`. |
| B | Same as A, but reuse MTK internals (`generate_connection_set`, `ConnectionVertex`, `variable_from_vertex`) through a new, non-overwriting BondGraph function | Less own code for namespacing | Merged connected components **lose bond direction**. Internal API, already rewritten once (v10.4.0). Not viable without re-walking the `connect` equations anyway. |
| C | **Redesign to local constitutive equations**: junction ports become plain Equality connectors (`e`, `f`, no `connect = bg`), each `Junction0/1` writes its own equations (`e_i` equal, `Σ sᵢ fᵢ = 0`, and dually for 1-junctions) from the signs it already receives (`flatinput`), and a bond is just `connect(a, b)` with Equality semantics | Pure public MTK. `mtkcompile` works directly with no pre-pass. Most future-proof. | Large redesign. Inter-junction bonds declared at model level (`connect(m1_j1.power, m2_j0.power)`) need a port per bond with orientation, so the public API changes. The `a▶b` bond-variable naming and the sign convention must be re-derived and re-tested against the literature (the DC-motor sign issue in `TODO.md`). |
| D | Keep the overwrites with `__precompile__(false)` | Smallest diff | Only possible on MTK ≤ v10.3 (the overwritten signatures no longer exist from v10.4). Blocks precompilation of BondGraph and every downstream package. Old stack does not resolve fresh (Groebner). Dead end. |
| E | Custom `AbstractSystem` subtype dispatching MTK internals | No overwriting | Explicitly discouraged by the MTK docs; heavy; still internal API. |

For `@named` tuple support: MTK's macro rejects `@named a, b = f(...)` (`split_assign` throws, MTKB `systems/abstractsystem.jl#L2796-L2801`). Options: (1) drop it (tests 361-443 switch to `coneqs` or an explicit `name`); (2) a BondGraph macro `@bgnamed`. (1) is the smaller diff.

## 4. `System`, `mtkcompile`, `t`/`D`, `@mtkmodel`, initialization: effects on examples and tests

- **`ODESystem` → `System`** (v10.0.0): same positional form `System(eqs, t, vars, pars; name)`. `ODESystem` still works with a depwarn (MTKB `deprecations.jl#L45-L60`).
- **`structural_simplify` → `mtkcompile`** (v10.0.0, **verified**: NEWS L374-379; alias with depwarn in MTKB `deprecations.jl#L9-L23`). `@mtkbuild` → `@mtkcompile`.
- **`t`/`D`**: `ModelingToolkit.t_nounits` and `ModelingToolkit.D_nounits` are `@public` (MTKB `ModelingToolkitBase.jl#L510`). `@variables t` used as the independent variable triggers a warning (MTKB `utils.jl#L154-L163`). Recommend `using ModelingToolkit: t_nounits as t, D_nounits as D` in `bg.jl`, keeping `BondGraph.t`/`BondGraph.D` for the examples (`using BondGraph: t, D`).
- **`@mtkmodel`**: deprecated in v11 and moved to SciCompDSL.jl (NEWS L328-335). BondGraph does not use it. Do not adopt it for the docs.
- **Problems**: `ODEProblem(sys, op, tspan)` with `op` merging u0 and parameters (v10, NEWS L421-429). The examples' `ODEProblem(sys, [x => v, ...], tspan)` already fits. The system must be compiled (`mtkcompile`) or `complete`d (v9).
- **`reducedobs`** builds `ODESystem(eqs; name)`, which no longer exists (no iv) and returns an incomplete system that `ODEProblem` would reject. Replace it with `full_equations(mtkcompiled_sys)` for display, and pass the `mtkcompile` result to `ODEProblem`.
- **Initialization** (v9 init system; v11 `initial_conditions`/`bindings`/`guesses`, NEWS L203-311): all constant variable defaults become `initial_conditions`. The init system includes algebraic and observed equations plus those initial conditions (NEWS L238-254). `Power` gives every `e`/`f` an initial value and `Damper` sets `f = u = 1.0` (default) while `e = 0`. After tearing, many of these are observed, so initialization can be over-determined or inconsistent (**UNVERIFIED**, needs a run). Recommendation: connector `e`/`f` use `[guess = ...]` (`getguess` exported at MTKB `ModelingToolkitBase.jl#L416`, `setguess` `@public` at `#L516`), and only state-carrying elements get initial conditions. The examples already pass explicit u0 to `ODEProblem`.
- **Forcing terms**: examples use `@parameters F(t)` + `substitute(sys, Dict(F => sin(t)))`. In v11 this must become `@discretes F(t)` (NEWS L164-201), or better, pass the expression to `Se(...)` directly.
- **Strict unknowns** (v10.0.0): bond variables created by `gen_con_name`/`rename` must be added to the system's unknowns (see inventory).

## 5. Minimum Julia version

- MTK v11.45.4: `julia = "1.10"` ([Project.toml#L135](https://github.com/SciML/ModelingToolkit.jl/blob/v11.45.4/Project.toml)). ModelingToolkitBase v1.77.4: `1.10`. Symbolics v7.45.0: `1.10`. SymbolicUtils v4.51.0: `1.10`.
- History: MTK's own compat said `1.9` until at least v11.20.0 and `1.10` from v11.30.0 (`gh api .../contents/Project.toml?ref=v11.20.0|v11.30.0`). But SymbolicUtils 4.0.0 already required 1.10, so every MTK v11 install has effectively needed Julia ≥ 1.10. Julia 1.10 is also where the method-overwrite error starts, so there is no Julia version where MTK v11 and the current `src/mtk.jl` can coexist.

## 6. Recommendation and migration plan

**Target:** `ModelingToolkit = "11"` (tested on 11.45.x), `Symbolics = "7"`, `SymbolicUtils = "4"`, `julia = "1.10"`. Add `Setfield = "1"`; drop `DomainSets`. Rationale: v11 is the only maintained line. v10.x already has the new connection internals, so it gives no compatibility benefit, and moving to it would mean a second migration (SU 3 → 4, `defaults` → bindings) later.

Ordered steps (each small, each ending in a green or known-red test run):
1. **Dead-code cleanup on the old stack**: delete the commented code in `mtk.jl:95-244`, the unused imports (`Symbolic`, `FnType`, `similarterm`, `namespace_*`, `gensym`), `It`/DomainSets, and the stale exports (`renamevars`, `addsubsys`, `latexify`). Tests stay green on 8.71.
2. **Introduce the `Bond` record and `expand_bonds` (approach A) on the old stack**: walk `connect` equations instead of using `ConnectionSet`; adapt `csets2dict`/`csets2adjmtx`/`generate_graph` to `Bond`. Make `simplifysys` = `structural_simplify(expand_bonds(sys))` and delete the `expand_connections`/`generate_connection_set` overrides. Assert identical equations against the current outputs (golden tests). **Riskiest step**: namespacing, bond direction and the sign rules in `adjmtx2eqs` must reproduce exactly. Do it while the old stack is still available as an oracle.
3. **Drop tuple `@named`**: delete the `split_assign`/`single_named_expr` overrides and update `test_ports.jl` (or add `@bgnamed`). After this, `src/mtk.jl` is empty: delete it.
4. **Symbolic API renames** (still on the old stack where possible): `istree`→`iscall`, `!istree`→`issym` in `isindependent`, import `getname`/`rename`/`getmetadata`/`setmetadata` from Symbolics/SymbolicUtils, `power.name`→`nameof(power)`, `states`→`unknowns` in examples.
5. **Bump compat** to MTK 11 / Symbolics 7 / SU 4 / Julia 1.10, with a fresh resolve (no Manifest). Fix: `ODESystem`→`System`, `structural_simplify`→`mtkcompile`, `t_nounits`/`D_nounits`, `get_connection_type(unwrap(x))`, and add the bond variables to the unknowns.
6. **Initialization and examples**: switch connector defaults to guesses, replace `reducedobs` with `full_equations`, `@parameters F(t)` → `@discretes` or direct expressions, then run every example end to end.
7. CI green (fresh resolve), then docs.

**Open questions for the maintainer**
1. Approach A (keep the junction/`connect` API with a mandatory pre-pass) or C (local constitutive equations, works with plain `mtkcompile`, but the API changes)? A is the shorter path. C is the long-term clean one.
2. Depend on full **ModelingToolkit** (MIT, but pulls AGPL-3.0 StateSelection/ModelingToolkitTearing, NEWS L337-353), or only on **ModelingToolkitBase** (MIT, simple `mtkcompile` without index reduction)? BondGraph is Apache-2.0. Bond-graph models with derivative causality (e.g. rigidly coupled inertias) need index reduction.
3. Drop the tuple form of `@named` or keep it via a BondGraph macro?
4. Should calling `mtkcompile` on an un-preprocessed BG model be made to **error** (e.g. by not using `connect = bg` and checking for unprocessed bonds) rather than silently produce Equality equations?
5. Initial values: should connector `e`/`f` keep user-settable values (as guesses) or be removed?
6. Keep `BondGraph.t`/`D` as the package's time variable (aliasing `t_nounits`), or tell users to import from MTK?

**UNVERIFIED items (need a Julia run on the target stack):** resolution of `ModelingToolkit.@set!`/`ModelingToolkit.getname`; the exact initialization failure mode with the current connector defaults; `substitute` on compiled systems; `unwrap`/`iscall` on plain numbers passed as `g`/`r`; `hasproperty(sys, :pin)` on `System`; `deepcopy` of hash-consed `BasicSymbolic` in `add_idx`.
